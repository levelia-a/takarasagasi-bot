# 宝探しBot

Python 3.12以上・discord.py・MySQL 8以上を使うDiscord Botです。
LIA残高との連携は未実装です。参加費と報酬は仮想の値として表示・記録します。

## 構成

```text
main.py             起動・DB接続の初期化・コマンド同期
config.py           環境変数と接続設定
consts/             難易度・初期設定・Discord ID
commands/           /takara・/takara_admin
views/              ボタン・モーダル・Discordへの表示
services/           業務処理・トランザクション管理
services/db_service.py  MySQL接続プール・接続の取得と解放
repositories/       渡されたカーソルでSQLを実行
database/tables.py   手動実行用のテーブル定義SQL
tests/              ゲームルール・MySQL結合テスト
```

依存方向は `commands/views → services → repositories` です。
サービスとレポジトリのメソッドは `@staticmethod` で定義し、
`await SettingsService.get_all()` や `await SettingsRepository.get_all_settings(cursor)` のように
クラス名から直接呼び出します。インスタンスの生成や受け渡しは不要です。
`DbService` はプロセス内で1つの接続プールを共有し、接続の取得・解放を管理します。
起動時に `await DbService.connect(config.database)`、終了時に `await DbService.close()` を呼びます。
1プロセス・1イベントループで1つのBotを動かす構成です。
設定変更用のロックは `SettingsService` で共有します。
各ゲームの進行状態とロックは `Exploration` インスタンスに保持し、Viewも画面ごとに生成します。
各サービスが接続を取得し、設定更新＋管理ログ保存などの処理単位で
`begin / commit / rollback` を実行します。レポジトリは同じ接続のカーソルを受け取り、SQLを実行して結果を返します。
初期設定の補完・型変換・結果の組み立てはサービスの役割です。
単独の読み取りや単一INSERTはautocommitを使い、明示的なトランザクションを開始しません。

レポジトリの関数名は `操作_対象_条件` のsnake_caseで統一します。
`get`・`insert`・`update`・`upsert`・`delete` を区別し、対象テーブルやデータを名前に含めます。
条件で絞る場合は `by_user_id` など、集計単位は `grouped_by_difficulty` などで表します。
固定の取得件数やロックの有無も、`latest_10`・`for_update` として明記します。
例：`get_all_settings`、`upsert_setting_by_key`、`insert_admin_log`。
結果保存は既存行を上書きしないため、`insert_statistics_record_if_session_id_not_exists` としています。

各ディレクトリは `__init__.py` を置かない暗黙の名前空間パッケージとして扱います。
この仕組みはPython 3.3以降で利用できますが、このBotの動作要件はPython 3.12以上です。
プロジェクトのルートディレクトリで、以下の起動・テストコマンドを実行してください。

## セットアップ

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

宝探しBot専用のMySQLデータベースを用意し、RailwayのMySQLターミナルで
`database/tables.py` の `TABLES_SQL` 内のSQLを手動実行してください。
作成するテーブルは `settings`・`statistics`・`user_progress`・`user_progress_events`・`unlock_notifications`・`active_explorations`・`admin_logs` の7つに加え、`party_guild_locks`・`parties`・`party_members` の計10テーブルです。`user_progress` はユーザーごとの初級・中級の探索回数を保存します。`user_progress_events` はDB確定結果が不明な再試行でも二重加算しないため、探索単位のIDを冪等性キーとして保持します。正常完了直後には削除しません。`unlock_notifications` は解放判定には使わず、Discordへの解放通知が実際に表示された後で通知済みとして記録します。`active_explorations` はユーザーIDを主キーにした5分期限の開始枠で、複数Botプロセスが一時的に重なっても同じユーザーの同時進行を防ぎます。難易度の解放状態そのものは保存せず、現在の探索回数と現在の解放条件を比較して判定します。
その後、`.env` に接続情報を設定してください。
他BotのDBには接続しないでください。`settings` など汎用名のテーブルを使用します。

| 変数 | 内容 |
| --- | --- |
| `DISCORD_TOKEN` | Botトークン（必須） |
| `GUILD_ID` | コマンドを登録するサーバー。省略時は `consts/discord.py` の値 |
| `MYSQL_URL` | `mysql://user:password@host:port/database`。指定時は個別設定より優先 |
| `MYSQLHOST` / `MYSQLPORT` | MySQL接続先。ポートの既定値は3306 |
| `MYSQLUSER` / `MYSQLPASSWORD` | MySQL認証情報 |
| `MYSQL_DATABASE` | 専用のデータベース名 |

`MYSQL_URL` を使わない場合、`MYSQLHOST`・`MYSQLUSER`・`MYSQL_DATABASE` は必須です。
従来の `DISCORD_GUILD_ID`・`MYSQL_HOST`・`MYSQL_PORT`・`MYSQL_USER`・`MYSQL_PASSWORD` も使用できますが、個別設定では上表の名前を優先します。
URLのユーザー名やパスワードに記号がある場合はパーセントエンコードしてください。
SSLなどのURLクエリ指定には対応していません。TLS必須の接続先は接続設定の追加が必要です。

```sh
python -X pycache_prefix=.cache/pycache main.py
```

`-X pycache_prefix=.cache/pycache` により、キャッシュをプロジェクト直下の
`.cache/pycache/` にまとめます。内部には元のパスに対応した階層が作られますが、
各ソースフォルダーには `__pycache__` を作りません。`.cache/` はGit管理対象外です。
このオプションを付けずにPythonを実行すると、通常の `__pycache__` が再び作られます。
同じターミナルで常に集約したい場合は、プロジェクトのルートで
`export PYTHONPYCACHEPREFIX="$PWD/.cache/pycache"` を実行すれば、`python main.py` でも同じ保存先になります。
設定はPython起動前に必要なため、Botが読み込む `.env` には記載しません。
参照: [Pythonのキャッシュ保存先設定](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPYCACHEPREFIX)。

起動時はMySQLへ接続した直後に必須7テーブルの存在・InnoDB・必要列の型とNULL許容・PRIMARY KEY・保存に必要なDEFAULTとAUTO_INCREMENTを検査します。`statistics.session_id` と `active_explorations.session_id` は単独列全体のUNIQUE制約も検査し、不一致があれば起動を中止します。テーブル作成・変更・データ移行は行いません。
`settings` は空の状態でも使用できます。未登録項目は `consts/treasure.py` の初期値を使い、管理画面で変更した項目をDBに保存します。
Bot用DBユーザーには専用DBの `SELECT / INSERT / UPDATE / DELETE` 権限が必要です。
テーブルを手動作成するユーザーには別途 `CREATE` 権限が必要です。
サーバーへのコマンド同期も起動時に行います。定義変更後は再起動してください。
Botの招待には `bot` と `applications.commands` スコープ、および投稿先でメッセージ送信・埋め込みリンク権限が必要です。

## 操作

### 地図・ステージ設定の管理

`/takara_admin` →「地図・ステージ設定」から、以下を再起動なしで変更できます。

- 地図の出現率：銅・銀・金。合計100%以下、残りは通常地図です。
- 地図の成功率補正：銅・銀・金それぞれ0〜100の整数ポイント。補正後の成功率は100%が上限です。
- 開始ステージの出現率：迷いの森・古代遺跡・秘境の神殿。合計100%。
- レア以上の抽選倍率：ステージごとに1〜100倍。
- レア度の基本配分：ノーマル・レア・エピック・レジェンド。合計100%。保存すると全難易度に適用します。
- 難易度別の宝物設定：表示順に10種類の基本出現率とレア度を入力します。出現率は合計100%、レア度は日本語名または`normal / rare / epic / legendary`です。

出現率と倍率は小数第2位まで入力できます。レア度配分を適用中は、同じレア度内の宝物の比率を維持して
指定の配分へ換算します。正の配分を指定するレア度には、各設定済み難易度に出現率が正の宝物が必要です。
「レア度配分を解除」で宝物ごとの確率へ戻せます。初期状態は未適用で、既存カタログの確率を維持します。
宝物の個別設定は`data/treasures.json`の並び順に対応するため、管理パネルで設定後にファイルの並び順を変更する場合は再設定してください。

変更は既存の`settings`と`admin_logs`へ同時に保存し、再起動後も保持します。DB構造の変更はありません。
進行中の宝探しは開始時の設定・宝物確率を維持し、次の宝探しから新しい設定を適用します。
管理画面の操作は管理者限定です。不正な値・合計確率は保存せず、エラーを表示します。

管理パネルの「履歴」は新しい順に10件ずつ表示し、「前へ」「次へ」で切り替えます。
履歴画面のユーザー選択欄で名前を検索・選択すると、そのユーザーだけの履歴を表示します。
検索条件はページ移動後も保持され、「全ユーザー」で解除できます。対象変更時は1ページ目に戻ります。
通常・テスト両方の履歴が対象です。開いた管理者本人だけが操作でき、5分間操作しないと終了します。
閲覧中の新規結果は画面を開き直すと反映されます。閲覧済みページはその画面内に保持するため、
テスト履歴を削除した後の最新状態も開き直して確認してください。管理ログは従来どおり最新10件です。

### 探索ランキング

- 管理者が掲載先で `/takara_ranking_panel` を実行すると常設ランキングを設置します。
- 起動後に1回、その後6時間ごとに集計して同じメッセージを編集します。午前0時・正午固定ではなく起動時刻が基準です。
- `/takara_ranking` でも直近の集計結果を閲覧できます。閲覧時の再集計は行いません。
- 「合計探索成功回数」「累計換金額」「一撃最高額」の各上位10人を表示します。同値は同順位、表示順はユーザーID順で最大10人です。値が0の人は各項目の対象外です。
- 全難易度・全期間の保存済み通常プレイが対象です。成功回数は失敗終了前の成功も含みます。進行中・タイムアウト・再起動で未確定のゲームは含みません。
- 累計換金額は確定報酬の合計（挑戦料を引く前）、一撃最高額は1回の宝探しの確定報酬の最大値です。実際のLIA残高との連携はありません。既存の結果履歴も含みます。
- 設置先は既存の `settings` テーブルに保存するためDB構造の変更は不要です。1Botにつき常設1件で、再実行時は既存メッセージを更新します。移設する場合は旧メッセージを削除して新しい場所で再実行してください。
- メッセージが削除された場合は管理者が設置コマンドを再実行してください。送信・埋め込みリンク権限が必要です。
- 集計・投稿失敗はログに記録して次の定期処理で再試行します。集計失敗時は前回の結果を維持し、メッセージには最終集計日時を表示します。
- `RANKING_INTERVAL_SECONDS` で間隔を変更できます（既定21600秒＝6時間、60〜86400秒）。変更後は再起動してください。

- `/takara`：公開トップ画面から「1人でプレイ」「パーティーを組む」を選択。以降の画面は本人にだけ表示します。
- `/takara_admin`：Discordの管理者権限が必要。価格・確率・回数・難易度解放条件・運営状態・テストモードの変更、統計・履歴・管理ログの確認、テスト履歴の削除ができます。
- 成功するたびに難易度別の宝物を1個抽選し、その価格を合計します。同じ宝物も複数回発見できます。引き返し・完走は宝物合計、失敗は0 LIAで確定します。挑戦料は報酬計算に使用しません。
- 初期設定は初級 `1000 / 60% / 5回`、中級 `5000 / 50% / 7回`、上級 `10000 / 40% / 10回` です。初級を10回探索すると中級、中級を20回探索すると上級に挑戦できます。成功・失敗に関係なく通常プレイの探索判定ごとに1回加算し、テストモードは進捗に含めません。同じ探索の保存を再試行しても進捗は二重加算しません。難易度解放進捗はこの機能の導入後から全員0回で記録を開始し、過去履歴からの移行は行いません。同一ユーザーは同時に複数の宝探しを開始できません。解放判定と解放通知は保存済みの探索回数と現在の管理者設定を比較するため、必要回数を引き上げて探索回数が条件未満になった場合は再び挑戦できなくなります。
- 挑戦料・成功率・最大回数・テスト判定・宝物設定は開始時に固定します。管理変更は次のゲームから適用されます。運営OFFは新規開始を停止します。
- 探索回数は1〜215、最大報酬は65桁以内です。最大回数1の場合も最初の成功で完走します。
- 同じゲームの結果は重複保存しません。通常統計からテスト結果を除外します。
- 操作期限は5分です。途中のゲームはメモリ上だけに保持し、タイムアウト・再起動時は精算も結果保存も行いません。入口パネルは再起動後も使用できます。
- 初回探索の処理中は追加のボタン操作を受け付けません。画面にボタンが表示された後のDB・Discordエラーでは同じセッションを再操作でき、未保存の探索は再抽選せず保存を再試行します。初回判定前にエラーになった場合は、再操作でまず初回探索を実行します。
- 開始枠の期限切れや所有者交代を検出したセッションは操作を終了します。進捗・結果の保存時にも有効な所有権を確認し、同一transactionで開始枠の行ロックを保持するため、保存中に別セッションへ所有者が切り替わりません。
- 時刻はMySQLセッションのJSTで記録します。

## 宝物設定と保存範囲

### 宝の地図

宝探し開始時に地図を1回抽選します。「金の初級の宝の地図を手に入れた！」のように
地図の種類と難易度を開始Embedに表示します。通常は青、銅・銀・金はそれぞれ対応色です。
地図の銅・銀・金の色は開始画面で表示します。探索結果のEmbedは開始時に選ばれたステージのテーマ色で表示します。
地図の効果はその宝探しの全探索判定に有効で、終了後に次のゲームへ持ち越しません。
開始後のDB保存再試行・ボタン操作では地図を再抽選しません。

出現率の仮設定は通常95.7%、銅3%、銀1%、金0.3%。成功率への加算は通常0、銅5、銀10、金20ポイント、
補正後は100%が上限です。管理パネルの「地図・ステージ設定」で変更できます。難易度別の元の成功率は既存設定を使います。
テストモードでも地図を表示しますが、「必ず成功」「必ず失敗」の判定が優先されます。
地図はセッション内だけに保持し、DB構造の変更はありません。

### ステージと宝物レア度

宝探し開始時にステージを1回抽選し、終了まで同じ場所を探索します。
開始画面から場所とレア補正を表示し、途中の探索・失敗・撤退・DB保存の再試行では再抽選しません。
設定変更も開始済みの宝探しには適用しません。次の宝探しで新しい設定を使って抽選します。
成功率は難易度・地図・協力イベントで決まり、ステージはレア以上の宝物の重みに影響します。
失敗時はどのステージでも宝物を獲得できません。

仮設定は🌲迷いの森80%・🏛️古代遺跡17%・⛩️秘境の神殿3%。森は元の宝物確率、遺跡はレア以上の抽選重みを2倍、神殿は4倍にして、
全体を100%に換算します（実際の当選確率がそのまま2倍・4倍になる意味ではありません）。
ノーマル90%・レア10%なら、補正後のレア率は森10%、遺跡約18.2%、神殿約30.8%です。
レア・エピック・レジェンドの間の確率比は維持します。元の確率0の宝物は出現しません。
全宝物がノーマル、または全宝物がレア以上の場合は比率が変わらず、補正による変化はありません。
管理パネルの「地図・ステージ設定」でステージの出現率・倍率を変更できます。DB未登録時の初期値は`consts/balance.py`です。
以前の探索色設定は読み込み時に青→森・緑→遺跡・赤→神殿へ引き継ぎます。
新しい`stage_*`設定がある項目はそちらを優先します。旧設定行や履歴の削除・テーブル変更は不要です。

初期バランス案は宝物全体でノーマル75%・レア20%・エピック4%・レジェンド1%です。
各10種類の配分例はノーマル5種類を各15%、レア3種類を8%・7%・5%、エピック4%、レジェンド1%。
この配分なら成功時のレア以上は森25%・遺跡40%・神殿約57.14%になります。
レジェンドは森1%・遺跡1.6%・神殿約2.29%です。
これは仮起動用の出現頻度調整で、本番カタログには自動適用しません。価格と挑戦料の収支は別途調整が必要です。

`data/treasures.json` の `beginner`・`intermediate`・`advanced` に各10種類を設定します。
本番用30種類の価格・確率は未確定のため、現在はすべて空配列です。
空配列の難易度は「宝物設定が未完了」と表示して開始を止めます。テストモードも同様です。
仮の価格・確率を本番へ補完しません。架空データは `tests/treasure_fixtures.py` 内だけで使用します。

各宝物には次の項目を指定し、対応難易度は所属する配列で決まります。

| 項目 | 内容 |
| --- | --- |
| `id` | 全難易度で重複しない1〜80文字のID |
| `name` | 改行を含まない1〜100文字の表示名（絵文字可） |
| `price` | 0以上・65桁以内の整数。単位はLIA |
| `probability_percent` | 探索成功後の出現確率（百分率）。数値または小数の文字列。難易度ごとの合計は正確に100% |
| `rarity` | `normal`（ノーマル）・`rare`（レア）・`epic`（エピック）・`legendary`（レジェンド）。既存設定との互換性のため省略時は`normal` |

確率0の宝物は抽選されません。設定の読み込み失敗、種類数・ID・価格・確率の不正はエラーにします。
成功率とは独立した抽選で、小数の確率も整数の重みに変換して扱います。
抽選可能な宝物の最高価格 × 最大探索回数がMySQLの保存上限（65桁）を超える設定は受け付けません。
挑戦料は独立して65桁以内かを検証します。宝物データの変更は次の探索セッションから適用されます。

探索成功時は今回の宝物名・価値・探索回数・個数・合計価値を表示します。
「宝物一覧」は本人だけが閲覧でき、長い一覧は2000文字以内のページに分割します。
終了後は一覧の閲覧ボタンだけを残します（5分で終了）。失敗時は「失った宝物」として表示します。
保存の再試行では同じ宝物を保持し、再抽選・追加・価格の二重加算を行いません。
探索失敗も進捗1回に含め、テストモードは進捗に含めません。

DB変更はありません。`statistics.start_price` は挑戦料、`final_reward` は撤退・完走時の宝物合計、失敗時は0です。
既存の統計履歴は書き換えません。`found_treasures` はID・名前・価格・発見した探索回数をセッション内に保持し、
失敗しても消去しませんが、個別宝物の履歴はDBへ保存しません。再起動後に個別宝物を復元することはできません。
LIAは表示のみで、実際のユーザー残高の減算・加算は行いません。

## 検証

### パーティー

`/takara` は「1人でプレイ」「パーティーを組む」の公開トップ画面を表示します。
「1人でプレイ」は本人専用の難易度選択画面に進み、従来どおり探索できます。
「戻る」で本人専用のトップへ戻ります。既存の公開難易度パネルも引き続き使用できます。

「パーティーを組む」は通常VCへの参加が必要です。現在のVCの募集一覧から選んで参加するか、
「パーティーを作成」で自分がリーダーの募集を作ります。1人でも募集でき、2人以上で成立します。
人数上限は設けません。同じVCで複数のパーティーを作れます。Bot・ステージチャンネルは対象外です。
所属はサーバーごとに1人1パーティーです。所属中は自分のメンバー一覧を開きます。
募集一覧・メンバー一覧は10件ずつ表示し、「前へ」「次へ」で全件確認できます。

全員が「脱退する」を使用でき、リーダーのみ「解散する」を使用できます。
VC退出・移動で自動脱退し、リーダー脱退時は参加順（同時刻ならユーザーID順）に引き継ぎます。
1人なら募集を継続し、0人になると削除します。VC情報が取得できない間は所属を削除しません。
所属はMySQLに保存し、起動後・VC移動時・各操作時・60秒ごとに現在のVCと照合します。
停止中の退出・移動も復帰後の照合で反映します。ただし停止中に退出して同じVCへ戻った履歴は判定できません。

パネルは開いた本人だけが操作でき、5分間操作しないと操作期限が切れます。
他メンバーの変更は「更新」で表示へ反映します。期限が切れても所属は維持し、トップから再表示できます。
参加・脱退・解散はその時点のVC・所属・リーダー権限を再確認し、古い画面から別の所属は変更できません。
サーバー単位のDB行ロックと所属の主キー制約で、同時作成・同時参加による二重所属を防ぎます。
共同探索・パーティー特典は今回の対象外です。下記のVC人数ボーナスは従来のままです。

既存DBには `src/sql/20260925_parties.sql` を先に適用してください（再実行可能・既存データ変更なし）。
新規DBは `database/tables.py` の `TABLES_SQL` または同一定義の `src/sql/createTable.sql` を使用します。

### VC協力ボーナス

宝探し開始時に、探索者と同じ通常ボイスチャンネルにいる人間の人数（本人を含む・Botを除く）を数えます。
VC未参加・1人・ステージチャンネルは通常探索です。ミュート中でも同じVCにいれば数えます。

| 同じVCの人数 | 追加探索上限 | レア以上の重み | 協力イベント発生率 |
|---|---:|---:|---:|
| 2〜3人 | ＋1回 | 1.2倍 | 10% |
| 4〜5人 | ＋2回 | 1.4倍 | 20% |
| 6人以上 | ＋3回 | 1.6倍 | 30% |

「協力探索イベント」は各自の宝探し開始時に1回抽選します。当選後、次の4種類から1つ選び、
通常のVCボーナスに追加して、その宝探し全体へ適用します。

| イベント | 当選後の出現割合 | 追加効果 |
|---|---:|---|
| 🗺️ 隠し通路を発見！ | 40% | 探索上限＋2回 |
| 💎 宝物の気配 | 30% | レア以上の重み1.5倍 |
| 🛡️ 仲間の道案内 | 20% | 成功率＋5ポイント |
| 🌟 古代の宝物庫 | 10% | 探索上限＋2回・レア以上の重み1.5倍 |

イベント当選率と当選後の種類の割合は別です。例えば6人以上で宝物庫が出る確率は30%×10%＝3%。
宝物庫の場合、6人以上ではVCボーナスと合計して探索＋5回・レア以上の重み2.4倍となります。
道案内の成功率は地図補正に加算し、合計100%が上限です。追加された探索を進めるかは任意で、途中撤退できます。
段階は累積せず、到達した最高段階だけを使います。最大探索回数は追加分込みで215回までです。
人数・設定・イベント結果は開始時に固定し、途中の入退室・設定変更・保存の再試行では再抽選しません。
参加者間で探索結果や宝物を共有する仕組みではなく、同じVCへの参加による個人探索の協力ボーナスです。

レア・エピック・レジェンドの重みを同じ倍率で増やし、開始時のステージ倍率と掛け合わせます。
当選率そのものが倍になるわけではありません。元が0%の宝物は0%のままです。
例：基本レア以上25%の場合、森で6人以上・イベントなしなら約34.8%、宝物庫なら約44.4%です。
失敗時の報酬喪失、撤退、ランキング・進捗の保存方法は従来どおりです。

`/takara_admin` → **VC協力設定** でON/OFF・3段階の必要人数・追加探索回数・重み倍率・
イベント発生率、4種類それぞれの名前・追加探索・レア重み・成功率補正を編集できます。
「イベント4種類の出現割合」で4種類をまとめて指定し、合計100%にします。割合0%のイベントは抽選しません。
名前は改行なし1〜40文字。成功率補正は0〜100の整数ポイント。保存後は次の宝探しから適用されます。
必要人数は2〜100人で厳密な昇順、各効果とイベント率は人数増加で下がらない値とします。
追加回数は各0〜20回、各倍率は1〜5倍、発生率は0〜100%（倍率・確率は小数第2位まで）。
保存は既存の設定テーブルと管理ログを使い、テーブル追加は不要です。
旧一律イベント設定（`coop_event_extra`・`coop_event_multiplier`）は読み込み対象から外し、4種類の初期値に置き換えます。
報酬保存上限の検証には協力・イベントの最大追加回数も含めます。

Botは `Intents.voice_states` と音声参加者キャッシュを使用します。音声への接続・録音は行いません。
参考：[discord.pyのVoice States Intent](https://discordpy.readthedocs.io/en/stable/api.html#discord.Intents.voice_states)。

python -X pycache_prefix=.cache/pycache -m unittest discover -s tests -v

## Railway

Pythonサービスと、このBot専用のMySQLサービス／DBを用意します。
MySQLサービスを他Botと共用する場合も、データベースは分けてください。
現在のRailway環境では宝探し専用DB `takarasagasi` を使用し、このBotの `MYSQL_DATABASE` に指定します。
Bot側に `DISCORD_TOKEN`、`GUILD_ID`、`MYSQLHOST`・`MYSQLPORT`・`MYSQLUSER`・`MYSQLPASSWORD`・`MYSQL_DATABASE` の参照を設定します。
`GUILD_ID` は省略可能です。MySQL接続には個別設定の代わりに `MYSQL_URL` も使用できます（指定時は優先）。
`railway.json` の起動コマンドは `python -X pycache_prefix=.cache/pycache main.py` です。HTTPポートは不要です。
ビルドは `requirements.txt`、Pythonの指定は `.python-version` を使用します。
デプロイ前に必ず `database/tables.py` のSQLを先に実行し、10テーブルが正しい定義で存在することを確認してからBotコードを更新してください。スキーマ未更新なら起動時検査でBotが停止し、不足テーブル名をログの例外で確認できます。
コマンド同期は起動時に行うため、別途コマンド登録用のデプロイ処理は不要です。

起動しない場合はRailwayのBuild Logsで依存関係の導入、Deploy Logsで必須変数・MySQL接続・テーブル権限・Discord認証・コマンド同期を確認してください。

実装参照: [discord.py](https://discordpy.readthedocs.io/en/stable/ext/commands/api.html)、[aiomysql](https://github.com/aio-libs/aiomysql)。
